# user-management Specification

## Purpose

Defines user management for CorporateCashFlow: the Manager-only capability to create, list, edit, deactivate/reactivate, and reset passwords for users, always constrained by the caller's scope (a Global Manager acts across all subsidiaries and global scope; a Subsidiary Manager acts only within their own subsidiary and cannot mint Managers or global users). This capability enforces its authorization on the backend, generates initial passwords once and never re-discloses them, revokes outstanding sessions on a Manager-set password reset, and exposes a protected frontend route whose navigation link is visible to any Manager. It also completes the `subsidiaries` deactivation guard by making it verifiable against real users created here.

## Requirements

### Requirement: Manager-only access to user management

Every endpoint of the user-management capability SHALL require an authenticated user whose `role` is `Manager` (global or subsidiary-scoped). An `Editor` or `Auditor` SHALL be rejected with `403 Forbidden` on every endpoint and HTTP method. A request with no valid access token SHALL be rejected with `401 Unauthorized`. This coarse gate is enforced on the backend and is independent of frontend state; finer-grained scope rules (below) are layered on top.

#### Scenario: A Manager reaches the capability

- **GIVEN** an authenticated user whose role is `Manager` (any scope)
- **WHEN** they call any user-management endpoint
- **THEN** the request passes the Manager gate and scope rules are then applied

#### Scenario: Editor or Auditor is forbidden on every endpoint

- **GIVEN** an authenticated `Editor` or `Auditor` (any scope)
- **WHEN** they call any user-management endpoint with any HTTP method
- **THEN** the response is `403 Forbidden`
- **AND** no user is read, created, or modified

#### Scenario: Unauthenticated request is rejected

- **GIVEN** a request carrying no valid access token
- **WHEN** it calls any user-management endpoint
- **THEN** the response is `401 Unauthorized`

### Requirement: Create a user within the caller's scope

The system SHALL expose `POST /api/users` accepting `Name`, `Email`, `Role`, and `SubsidiaryId`. A **Global Manager** (`subsidiaryId == null`) MAY create a user of any role and any scope. A **Subsidiary Manager** (`subsidiaryId != null`) MAY create only an `Editor` or `Auditor`, and only bound to their own subsidiary; any attempt to create a `Manager`, or to bind the new user to a different subsidiary or to global scope, SHALL be rejected with `403 Forbidden`. `Email` SHALL be unique. The initial password SHALL be generated by the backend and returned exactly once in the create response; it is never emailed and never retrievable afterwards. The created user SHALL be `Active`. An `Editor` SHALL always have a non-null `SubsidiaryId`.

#### Scenario: Global Manager creates a global Manager

- **GIVEN** an authenticated Global Manager
- **WHEN** they `POST /api/users` with role `Manager` and a null `SubsidiaryId`
- **THEN** the response is `201 Created` with the new user and a one-time generated password
- **AND** the user is `Active`

#### Scenario: Subsidiary Manager cannot create a user for another subsidiary

- **GIVEN** an authenticated Subsidiary Manager scoped to subsidiary A
- **WHEN** they `POST /api/users` with a `SubsidiaryId` of subsidiary B
- **THEN** the response is `403 Forbidden`
- **AND** no user is created

#### Scenario: Subsidiary Manager cannot create a Manager

- **GIVEN** an authenticated Subsidiary Manager scoped to subsidiary A
- **WHEN** they `POST /api/users` with role `Manager` (even bound to subsidiary A)
- **THEN** the response is `403 Forbidden`
- **AND** no user is created

#### Scenario: Subsidiary Manager creates an Editor in their own subsidiary

- **GIVEN** an authenticated Subsidiary Manager scoped to subsidiary A
- **WHEN** they `POST /api/users` with role `Editor` and `SubsidiaryId` = subsidiary A
- **THEN** the response is `201 Created` with a one-time generated password
- **AND** the user is bound to subsidiary A

#### Scenario: Duplicate email is rejected

- **GIVEN** an existing user with a given email
- **WHEN** a Manager `POST`s a new user with that same email
- **THEN** the request is rejected with a validation error and no user is created

### Requirement: List users within the caller's scope

The system SHALL expose `GET /api/users` returning users the caller is entitled to see: a Global Manager sees all users; a Subsidiary Manager sees only users whose `SubsidiaryId` equals their own. Each entry SHALL include `Name`, `Email`, `Role`, `SubsidiaryId`, and `IsActive`. The password hash SHALL never be returned.

#### Scenario: Global Manager lists every user

- **GIVEN** an authenticated Global Manager and users across several subsidiaries and global scope
- **WHEN** they `GET /api/users`
- **THEN** the response is `200 OK` with all users, and no password hashes

#### Scenario: Subsidiary Manager lists only their subsidiary's users

- **GIVEN** an authenticated Subsidiary Manager scoped to subsidiary A
- **WHEN** they `GET /api/users`
- **THEN** the response is `200 OK` containing only users whose `SubsidiaryId` is A
- **AND** users of other subsidiaries and global-scope users are not returned

### Requirement: Edit a user's role and subsidiary within the caller's scope

The system SHALL expose `PUT /api/users/{id}` that updates a user's `Role` and `SubsidiaryId`. A Global Manager MAY set any role/scope. A Subsidiary Manager MAY act only on users of their own subsidiary and SHALL NOT elevate a user to global scope, to the `Manager` role, or move a user to another subsidiary — any such attempt SHALL be rejected with `403 Forbidden`. Editing SHALL preserve the invariant that an `Editor` has a non-null `SubsidiaryId`.

#### Scenario: Subsidiary Manager cannot elevate a user to global scope

- **GIVEN** an authenticated Subsidiary Manager scoped to subsidiary A and a user in subsidiary A
- **WHEN** they `PUT /api/users/{id}` setting `SubsidiaryId` to null (global)
- **THEN** the response is `403 Forbidden`
- **AND** the user is unchanged

#### Scenario: Subsidiary Manager cannot promote a user to Manager

- **GIVEN** an authenticated Subsidiary Manager scoped to subsidiary A and an `Editor` in subsidiary A
- **WHEN** they `PUT /api/users/{id}` setting role `Manager`
- **THEN** the response is `403 Forbidden`
- **AND** the user is unchanged

#### Scenario: Global Manager reassigns a user's role and subsidiary

- **GIVEN** an authenticated Global Manager and an existing user
- **WHEN** they `PUT /api/users/{id}` with a new valid role and subsidiary
- **THEN** the response is `200 OK` and the user's role and subsidiary are updated

### Requirement: Deactivate and reactivate a user within the caller's scope

The system SHALL expose `PATCH /api/users/{id}/deactivate` and `PATCH /api/users/{id}/reactivate`, toggling `IsActive` (soft delete). A user is never physically deleted, preserving audit history. The same scope rule applies: a Subsidiary Manager may act only on users of their own subsidiary; acting on a user outside their scope SHALL be rejected with `403 Forbidden`. A deactivated user is blocked from logging in (enforced by the `auth` capability).

#### Scenario: Manager deactivates then reactivates a user in scope

- **GIVEN** an authenticated Manager and an active user within their scope
- **WHEN** they `PATCH /api/users/{id}/deactivate`
- **THEN** the response is `200 OK` and the user's `IsActive` becomes `false`
- **AND** a subsequent `PATCH /api/users/{id}/reactivate` sets `IsActive` back to `true`

#### Scenario: Subsidiary Manager cannot deactivate a user outside their scope

- **GIVEN** an authenticated Subsidiary Manager scoped to subsidiary A and a user in subsidiary B
- **WHEN** they `PATCH /api/users/{id}/deactivate`
- **THEN** the response is `403 Forbidden`
- **AND** the target user is unchanged

### Requirement: Manager-set password reset revokes outstanding sessions

The system SHALL expose `PATCH /api/users/{id}/reset-password`, letting a Manager set a new password for a user directly (no self-service flow). The same scope rule applies. On success the user's password SHALL be updated and **all of that user's outstanding (non-revoked, non-expired) refresh tokens SHALL be revoked**, so a session established before the reset cannot be renewed. There is no email delivery.

#### Scenario: Reset lets the user log in with the new password and kills the old session

- **GIVEN** an authenticated Manager and a user within their scope who has an active refresh token
- **WHEN** the Manager `PATCH /api/users/{id}/reset-password` with a new password
- **THEN** the response is successful
- **AND** the user can log in with the new password
- **AND** the user's prior refresh token is rejected on any subsequent refresh

#### Scenario: Subsidiary Manager cannot reset a password outside their scope

- **GIVEN** an authenticated Subsidiary Manager scoped to subsidiary A and a user in subsidiary B
- **WHEN** they `PATCH /api/users/{id}/reset-password`
- **THEN** the response is `403 Forbidden`
- **AND** the target user's password is unchanged

### Requirement: Subsidiary deactivation guard verified against real users

The `Subsidiary` deactivation guard (defined by the `subsidiaries` capability) SHALL block deactivation while any **active** `User` is assigned to that subsidiary — now verifiable against users created through this capability, not only the development seed. Deactivating a subsidiary whose only assigned users are inactive SHALL succeed.

#### Scenario: A subsidiary with a real active user cannot be deactivated

- **GIVEN** a Global Manager creates a subsidiary and then creates an active `Editor` bound to it
- **WHEN** the Global Manager attempts to deactivate that subsidiary
- **THEN** the deactivation is blocked with the integrity error (active users still assigned)

#### Scenario: Deactivating the assigned user then unblocks the subsidiary

- **GIVEN** the same subsidiary whose only assigned user has since been deactivated
- **WHEN** the Global Manager attempts to deactivate the subsidiary
- **THEN** the deactivation succeeds and the subsidiary's `IsActive` becomes `false`

### Requirement: User-management screen visible to any Manager

The frontend SHALL provide a protected `features/users` route with a scope-respecting listing, plus create, edit-role/subsidiary, activate/deactivate, and reset-password actions. The navigation link and route SHALL be available to any `Manager` (global or subsidiary-scoped) and SHALL NOT appear for `Editor`/`Auditor`. The actions and targets presented SHALL reflect the signed-in Manager's scope (a Subsidiary Manager sees only their subsidiary's users and cannot create Managers or global users). The backend remains the source of truth for every rule.

#### Scenario: Manager sees and opens the users screen

- **GIVEN** a signed-in Manager (global or subsidiary-scoped)
- **WHEN** they view the App Shell navigation
- **THEN** a "Users" link is shown and opens the user-management screen

#### Scenario: Editor or Auditor never sees the users screen

- **GIVEN** a signed-in `Editor` or `Auditor`
- **WHEN** they view the App Shell navigation
- **THEN** no "Users" link is shown
- **AND** navigating directly to the users route is blocked
