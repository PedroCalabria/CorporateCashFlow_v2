## Why

Authentication exists, and subsidiaries can be created — but the only real user in the system is the temporary development seed from the `auth` capability. There is no way to provision the Managers, Editors, and Auditors that every downstream capability's RBAC depends on. `user-management` is capability #5 in the build order: it turns the `User` entity (created, but only ever read, in `auth`) into a fully managed aggregate, and it is the first capability whose authorization is a **scope asymmetry** rather than a single flag — a Global Manager governs everyone, while a Subsidiary Manager governs only their own subsidiary and can never widen a user's reach. It also closes the loop on the deactivation guard left partially verified in `subsidiaries`: only now do real (non-seed) active users exist to prove it against (`docs/requirements-document.md` §7, `docs/business-rules-formalization.md` §3).

## What Changes

- Add `POST /api/users` — creates a user (`Name`, `Email`, `Role`, `SubsidiaryId`) subject to the creation-scope rule: a **Global Manager** may create any role/scope; a **Subsidiary Manager** may create only `Editor`/`Auditor` bound to their own subsidiary (`docs/business-rules-formalization.md` §3, transition 1). The initial password is **generated by the backend and returned exactly once** in the create response — no email flow (out of MVP). `Email` must be unique.
- Add `GET /api/users` — lists users within the caller's scope: a Global Manager sees all; a Subsidiary Manager sees only users of their own subsidiary.
- Add `PUT /api/users/{id}` — edits `Role`/`SubsidiaryId` under the same scope rule: a Subsidiary Manager can **never** elevate a user to global scope or to the `Manager` role, nor move a user outside their subsidiary (`docs/business-rules-formalization.md` §3, transition 4).
- Add `PATCH /api/users/{id}/deactivate` and `PATCH /api/users/{id}/reactivate` — soft-delete via `IsActive`, governed by the same scope rule. A user is **never** physically deleted (`docs/business-rules-formalization.md` §3, transitions 2 and 3).
- Add `PATCH /api/users/{id}/reset-password` — a Manager sets a new password directly (no self-service "forgot password"; roadmap, `docs/requirements-document.md` §11). Resetting a password **revokes the user's outstanding refresh tokens**, so an old session cannot survive the change.
- **Revisit the `subsidiaries` deactivation guard**: with real user creation/assignment now in place, confirm the "no active `User` assigned" check works against real data (not just the `auth` dev seed). The `LedgerEntry`-pending half of that guard remains deferred to `ledger-entries` (its `TODO(ledger-entries)` stays).
- **Frontend** (`features/users`): a user-management screen — scope-respecting listing, create, edit role/subsidiary, activate/deactivate, reset password. Visible to **any Manager**; the available actions/targets vary by the signed-in Manager's scope. Adds the real nav link in the App Shell.

## Capabilities

### New Capabilities
- `user-management`: Manager-only provisioning and lifecycle of `User` accounts — create (with a one-time generated password), scope-filtered listing, edit of role/subsidiary, soft deactivate/reactivate, and Manager-set password reset that revokes outstanding sessions. Enforces the Global-vs-Subsidiary-Manager scope asymmetry on every endpoint, and rejects Editors/Auditors with `403`.

### Modified Capabilities
- `app-shell`: The `Persistent application layout` requirement's navigation now also exposes a real, Manager-only "Users" link (visible to any Manager, global or subsidiary-scoped), alongside the existing Global-Manager-only "Subsidiaries" link and the remaining placeholders.

## Impact

- **Backend**
  - **Domain**: `User` gains lifecycle behavior (`Create`, `UpdateRoleAndScope`, `Deactivate`, `Reactivate`, `SetPasswordHash`, touching `UpdatedAt`) — the `User` state machine (`docs/business-rules-formalization.md` §3) now has a real home. `IUserRepository` is extended (scope-filtered list, email-existence check, `SaveChangesAsync`). `IRefreshTokenRepository` gains a "revoke all active tokens for a user" operation (for password reset). A `Password` value/generator abstraction produces the one-time initial password.
  - **Application**: `UserManagementService` owning the scope-authorization logic (the Global-vs-Subsidiary asymmetry, read through `ICurrentUserService`), create/update/reset DTOs and validators, and a `ForbiddenOperationException` for scope violations. Reuses `IPasswordHasher` (from `auth`).
  - **Infrastructure**: `UserRepository` implementation extended; a secure random initial-password generator; refresh-token bulk revoke.
  - **Api**: `UsersController` behind a new `Manager` authorization policy (role `Manager`, any scope), with fine-grained scope enforcement delegated to the service and `ForbiddenOperationException` mapped to `403`.
- **Frontend**: new `features/users/` (list/create/edit/reset components, TanStack Query hooks, typed API client, Zod schemas), a Manager-gated route, an i18n namespace (en + pt-BR), and the real "Users" nav link in the App Shell (Manager-only).
- **Database**: no new tables — `Users` already exists. Behavior only (writes through the existing table; refresh-token revocation uses the existing `RefreshTokens` table).

## State Transitions Covered

Covers the **`User` state machine** (`docs/business-rules-formalization.md` §3) in full: rule 1 (create — Global Manager any role/scope; Subsidiary Manager only Editor/Auditor within own subsidiary), rule 2 (`Active` → `Inactive` deactivate), rule 3 (`Inactive` → `Active` reactivate), and rule 4 (edit role/subsidiary and force password reset, with a Subsidiary Manager unable to elevate scope or role). Physical deletion is never performed. Does **not** touch the `LedgerEntry`, `BankStatementImportBatch`, or `Subsidiary` state machines — but it **re-verifies** the `Subsidiary` deactivation guard (`docs/business-rules-formalization.md` §4, transition 3) against real users now that user creation exists.

## Out of Scope (explicitly deferred)

- **Physical deletion of a user** — never permitted; soft delete only (`docs/business-rules-formalization.md` §3).
- **Self-service "forgot password"** — roadmap (`docs/requirements-document.md` §11); only Manager-forced reset is in scope here.
- **Email delivery of credentials** — no messaging infrastructure in the MVP; the generated initial password is returned once in the API response and communicated out-of-band.
- **The `LedgerEntry`-pending half of the `Subsidiary` deactivation guard** — still deferred to `ledger-entries` (that entity does not exist yet); its `TODO(ledger-entries)` remains.
- **Any `LedgerEntry` business rule** — later capabilities.

## Testing Scope

Per `docs/development-workflow.md` §4: this change exposes multiple endpoints whose authorization is **non-trivial and scope-sensitive** — the Global-vs-Subsidiary-Manager asymmetry is exactly where an authorization bug would most easily slip through unnoticed. **Integration tests are expected**, covering every scope scenario: (1) a Global Manager creates a `Manager` with null `subsidiaryId` → success; (2) a Subsidiary Manager creating a user for **another** subsidiary → `403`; (3) a Subsidiary Manager creating a `Manager` → `403`; (4) a Subsidiary Manager editing a user to global scope → `403`; (5) a Subsidiary Manager listing users → sees only their own subsidiary's; (6) a Manager resets a user's password → the user authenticates with the new password **and** their prior refresh token is rejected; (7) an Editor or Auditor hitting any endpoint → `403`. Because the change also touches the `User` **state machine**, a **Domain unit test is expected** for the create/deactivate/reactivate/edit transitions. The re-verification of the `Subsidiary` deactivation guard is covered by an integration test exercising it against a **real** assigned user (superseding the seed-only check). Frontend behavior (scope-varying actions, Manager-only visibility) is verified manually against the running app.
