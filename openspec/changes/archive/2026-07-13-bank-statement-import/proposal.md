## Why

`ledger-entries` records the company's **internal** view of its money. Reconciliation — the whole point of a treasury system — needs the **external** truth to compare against: the bank's own statement. `bank-statement-import` is capability #7; it brings that external dataset into the system by letting a writer upload a bank-statement spreadsheet as a `BankStatementImportBatch` of `BankStatementLine` records (`docs/requirements-document.md` §3.6/§3.7), and it gives a Manager the batch-level escape hatch — rejecting a whole batch when the file is wrong (wrong period, wrong file, systemic error) instead of fixing it line by line (`docs/business-rules-formalization.md` §2.2, transition 2; §4.3). It deliberately stops short of the matching engine: lines land `Unmatched` and stay there until the `reconciliation` capability exists.

## What Changes

- Add the `BankStatementImportBatch` entity (`docs/requirements-document.md` §3.6) with the **full** status enum (`Processed`, `ProcessedWithErrors`, `Rejected`) and the `BankStatementLine` entity (§3.7) with the **full** status enum (`Unmatched`, `AutoMatched`, `ManuallyMatched`, `Invalidated`). Implement only the transitions this capability owns: batch creation (→ `Processed`/`ProcessedWithErrors`) and **transition 2** (batch → `Rejected`, lines → `Invalidated`) from `docs/business-rules-formalization.md` §2.2. The `AutoMatched`/`ManuallyMatched` line transitions belong to `reconciliation` and are left as explicit domain `TODO`s.
- Add `POST /api/bank-statement-imports` — upload a spreadsheet, creating one `BankStatementImportBatch` (`SubsidiaryId`, `ImportedBy`, `ImportedAt`, `FileName`) and its `BankStatementLine` records (each starting `Unmatched`). A **writer** — an `Editor` (own subsidiary only) or a `Manager` (own subsidiary, or any if global) — may import; an `Auditor` is rejected with `403 Forbidden`. Each line is validated (well-formed, parseable date/amount, credit/debit type) and checked for **duplication against every `BankStatementLine` already persisted for that subsidiary** — not merely against other rows in the same file — using the composite `Date + Amount + Description + SubsidiaryId` (`docs/requirements-document.md` §3.7; `docs/business-rules-formalization.md` §1.4, same pattern corrected in `ledger-entries`). Duplicate/invalid rows are **rejected and reported** in the upload result (row number + reason) without blocking the file's valid rows. The batch resolves to `Processed` (no rejected rows) or `ProcessedWithErrors` (at least one rejected row).
- Add `GET /api/bank-statement-imports` — paginated listing of batches (with line summary/status), **scoped by role**: an `Editor` sees only their own subsidiary; a `Manager` sees per scope (own, or all if global); an `Auditor` the same, strictly read-only.
- Add `PATCH /api/bank-statement-imports/{id}/reject` — a `Manager` (own subsidiary, or global) rejects the **entire** batch (all-or-nothing; no selective per-line invalidation in the MVP — `docs/business-rules-formalization.md` §2.3), with a **mandatory `RejectionReason`**. Effect in this change: `Batch.Status = Rejected` (`RejectedBy`/`RejectedAt` set) and every `BankStatementLine` in the batch moves to `Invalidated`. An `Editor` or `Auditor` is rejected with `403 Forbidden`. Rejection writes an `AuditLog` `Rejected` row (`docs/business-rules-formalization.md` §5). The reversal of matched `LedgerEntry` items back to `PendingReconciliation` (transition 8) is **NOT** implemented here — it depends on match links that only exist in `reconciliation`; left as an explicit domain `TODO`.
- **Frontend** (`features/bank-statement-import`): an upload screen with invalid/duplicate-row feedback (the same UX pattern already used by the ledger-entries import), a batch listing showing status, and a Manager-only reject action gated behind a modal that requires a reason. Adds the real "Bank Statements" nav link (replacing its placeholder) in the App Shell, visible to any authenticated user.

## Capabilities

### New Capabilities
- `bank-statement-import`: Spreadsheet upload of bank-statement batches with persisted-scope duplicate detection and per-row feedback, role/scope-based listing, and Manager-only full-batch rejection — covering `BankStatementImportBatch` transitions 1 (create → `Processed`/`ProcessedWithErrors`) and 2 (→ `Rejected`, lines → `Invalidated`) of `docs/business-rules-formalization.md` §2.2. Reuses the existing `AuditLog` sink (a `Rejected` row on rejection).

### Modified Capabilities
- `app-shell`: The navigation now exposes a real "Bank Statements" link (visible to any authenticated user), replacing its placeholder.

## Impact

- **Backend**
  - **Domain**: new `BankStatementImportBatch` and `BankStatementLine` entities; enums `BankStatementBatchStatus` (Processed/ProcessedWithErrors/Rejected) and `BankStatementLineStatus` (Unmatched/AutoMatched/ManuallyMatched/Invalidated); a `BankStatementLineSignature` value key for §1.4 duplicate detection; `IBankStatementImportRepository`. The batch aggregate owns `Reject(reason, by)` (guard: non-empty reason; from `Processed`/`ProcessedWithErrors`), which invalidates its lines; the `AutoMatch`/`ManuallyMatch` line transitions and the matched-`LedgerEntry` reversal are explicit `TODO` stubs owned by `reconciliation`. Reuses `AuditLog`/`AuditAction` from `ledger-entries`.
  - **Application**: `BankStatementImportService` (import with per-row validation + persisted-scope duplicate detection; scoped paginated list; reject with audit write), a bank-statement import parser + DTOs, reusing `PagedResult`/`PagedRequest`, `ICurrentUserService`, `ForbiddenOperationException`, and the audit-snapshot helper.
  - **Infrastructure**: EF Core configurations + a migration for `BankStatementImportBatches` and `BankStatementLines`; repository implementation; CSV parsing (mirroring the ledger-entries import machinery).
  - **Api**: `BankStatementImportsController` (`[Authorize]` + service-enforced role/scope), mapping `ForbiddenOperationException` → `403` and validation → `400`.
- **Frontend**: new `features/bank-statement-import/` (upload with invalid/duplicate feedback, batch list with status, Manager-only reject modal), TanStack Query hooks, a typed API client, Zod schemas, an i18n namespace (en + pt-BR), and the real "Bank Statements" nav link.
- **Database**: two new tables (`BankStatementImportBatches`, `BankStatementLines`) with FKs (`BankStatementImportBatches.SubsidiaryId → Subsidiaries`, `BankStatementLines.ImportBatchId → BankStatementImportBatches`, `BankStatementLines.SubsidiaryId → Subsidiaries`, nullable `BankStatementLines.MatchedLedgerEntryId` reserved for `reconciliation`).

## State Transitions Covered

Covers the **`BankStatementImportBatch` state machine** (`docs/business-rules-formalization.md` §2.2): **transition 1** (create → `Processed` when no rejected rows, or `ProcessedWithErrors` when at least one row is rejected; writer scoped) and **transition 2** (`Processed` | `ProcessedWithErrors` → `Rejected`; Manager only; mandatory `RejectionReason`; all `BankStatementLine` → `Invalidated`). It does **NOT** implement the `BankStatementLine` `AutoMatched`/`ManuallyMatched` transitions (§2.3) nor the matched-`LedgerEntry` → `PendingReconciliation` reversal that transition 2 ultimately triggers (§1.2, rule 8) — both depend on match links owned by `reconciliation` and are left as explicit domain `TODO`s. No `LedgerEntry`, `User`, or `Subsidiary` transitions are performed.

## Out of Scope (explicitly deferred)

- **Automatic matching engine and manual matching** (`docs/requirements-document.md` §4.1) — the `reconciliation` capability. Lines land `Unmatched` and stay there; the `AutoMatched`/`ManuallyMatched` transitions are enum values + domain TODOs only.
- **Reversal of a matched `LedgerEntry` to `PendingReconciliation` on batch rejection** (§1.2, rule 8) — depends on match links that only exist in `reconciliation`; left as an explicit domain `TODO` invoked from `Reject`.
- **Divergence justification/approval workflow** (§4.2) — the `reconciliation` capability.
- **Selective invalidation of individual lines within a batch** (§2.3) — a deliberate MVP simplification; only full-batch rejection is supported.
- **Any `AuditLog` viewing UI** — the `audit-trail` capability; this change only *persists* the `Rejected` audit row.

## Testing Scope

Per `docs/development-workflow.md` §4: this change touches a **real state-machine transition** (`BankStatementImportBatch`: `Processed`/`ProcessedWithErrors` → `Rejected`, cascading lines to `Invalidated`) and exposes **RBAC/scope-sensitive** write endpoints, so both test types are expected. **Domain unit tests** cover the rejection transition (`Reject` sets `Rejected` with `RejectedBy`/`RejectedAt`, requires a non-empty reason, invalidates every line, and is only allowed from `Processed`/`ProcessedWithErrors`). **Integration tests** cover the scope/duplicate scenarios: (1) Editor imports a valid statement in their own subsidiary → batch created, lines `Unmatched`, `Processed`; (2) Editor importing for another subsidiary → `403`; (3) Auditor importing or rejecting → `403` in both cases; (4) a row identical to an already-persisted line → that row rejected/reported as duplicate while the rest import, batch `ProcessedWithErrors`; (5) re-importing the exact same file → every row reported as duplicate, no new line created; (6) Manager rejects without a reason → rejected (reason mandatory); (7) Manager rejects with a reason → `Rejected`, all lines `Invalidated`, `AuditLog` `Rejected` written. Frontend behavior (upload feedback, batch list, reject modal) is verified manually against the running app.
