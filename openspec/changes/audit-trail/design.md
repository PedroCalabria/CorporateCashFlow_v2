## Context

`AuditLog` (Domain entity, `backend/src/CorporateTreasury.Domain/Entities/AuditLog.cs`) has existed since `ledger-entries` and is already written from two places: `LedgerEntryService` (`EntityType = "LedgerEntry"`, actions `Created`/`Updated`/`Deleted`) and `BankStatementImportService` (`EntityType = "BankStatementImportBatch"`, action `Rejected`). Both write through `IAuditLogRepository.AddAsync` (stage-only, flushed by the caller's own `SaveChangesAsync`, same unit of work as the business change). Nothing reads `AuditLog` yet — no controller, no query service.

`AccessLog` (`docs/requirements-document.md` §3.9, `docs/business-rules-formalization.md` §5) does not exist as code at all. The `auth` capability's login flow (`AuthService.LoginAsync`, `AuthController.Login`) already resolves everything needed to populate it (the looked-up `User?`, or `null` for an unknown email) but currently discards that distinction behind a single generic `null` result, by design, to prevent user enumeration in the HTTP response (`auth` spec, "Login with invalid credentials does not reveal which field was wrong"). That HTTP-facing guarantee must not change; only an internal side channel (the `AccessLog` row) gets the richer detail.

`403 Forbidden` responses in this codebase come from two independent mechanisms with no shared code path:
1. **Policy-based**: `ManagerHandler`/`GlobalManagerHandler` (`Api/Auth/*Authorization.cs`), registered against `[Authorize(Policy = ...)]` on a controller/action. A failed policy short-circuits inside the ASP.NET Core authorization middleware, before any controller code runs.
2. **Manual, service-level**: e.g. `LedgerEntryService`'s `EnsureWriter()`/`EnsureManager()`/`EnsureCanActOnSubsidiary()` throw `ForbiddenOperationException`, caught by the controller's `GuardedAsync` wrapper and mapped to `StatusCode(403, ...)`.

Only a piece of infrastructure sitting *after* both of these — i.e., after the response status code is already decided — sees both uniformly.

## Goals / Non-Goals

**Goals:**
- Introduce `AccessLog` as a first-class Domain entity, persisted the same way `AuditLog` already is.
- Get `LoginSuccess`/`LoginFailed` writes into the existing login flow with the correct nullable `UserId`, without weakening the anti-enumeration guarantee on the HTTP response.
- Get `AccessDenied` writes for *every* 403 in the system — present and future capabilities — from one piece of code, not per-controller instrumentation.
- Expose `GET /api/audit-log` and `GET /api/access-log`, both paginated/filterable, both scoped Manager/Auditor-only (own subsidiary or global), Editor forbidden.
- Ship the two-tab frontend screen and a real, role-gated App Shell nav link.

**Non-Goals:**
- No report/dashboard aggregation over these logs (that's `reports`; per the rule to confirm the read/write split, `IReportQueryService`/Dapper is reserved for that capability's aggregate queries — `audit-log`/`access-log` are simple paginated/filterable single-source reads, the same shape as `GET /api/ledger-entries`, so they go through an EF Core-backed repository like every other capability's list endpoint, not through Dapper).
- No retention/archival policy, no real-time alerting.
- No change to what `AuditLog` already captures (still `LedgerEntry` + `BankStatementImportBatch` rejection) — this change only makes it readable.
- No reverse-proxy-aware IP resolution (`X-Forwarded-For`, `UseForwardedHeaders`) — out of scope until a real reverse proxy exists in front of the API (see Open Questions).

## Decisions

**D1 — `AccessLog` and `AccessLogEventType` live in Domain, mirroring `AuditLog`.**
`Domain/Entities/AccessLog.cs` (private constructor + `Create(...)` factory, immutable, `Id`/`UserId` (nullable `Guid`)/`EventType`/`IpAddress`/`Timestamp` (UTC)) and `Domain/Enums/AccessLogEventType.cs` (`LoginSuccess`, `LoginFailed`, `AccessDenied`). `Domain/Interfaces/IAccessLogRepository` owns `AddAsync` (Domain-owned interface, Infrastructure-implemented — same DIP shape as `IAuditLogRepository`). Alternative considered: reuse `AuditLog` with a generic `EntityType = "AccessEvent"` — rejected because the shape genuinely differs (no `EntityId`/`OldValue`/`NewValue`, has `IpAddress`) and `docs/requirements-document.md` §3.9 specifies it as its own entity.

**D2 — Login writes `AccessLog` from `AuthService`, not `AuthController`.**
`AuthService.LoginAsync` already resolves the looked-up `User?` before collapsing to the generic `null`/`AuthTokens` result; that's the only place with the nullable-`UserId` distinction. `LoginAsync` gains an `ipAddress` parameter (Application services don't touch `HttpContext`, so the Api layer resolves `HttpContext.Connection.RemoteIpAddress` and passes it as a plain string) and writes the `AccessLog` row on every branch: `LoginFailed` with `UserId = null` (email not found), `LoginFailed` with `UserId = user.Id` (known email, wrong password, or inactive account), or `LoginSuccess` with `UserId = user.Id`. The row is staged via `IAccessLogRepository.AddAsync` and flushed by the same `SaveChangesAsync` call the method already makes (`_refreshTokens.SaveChangesAsync` on success; a new explicit save on the failure branches, which currently persist nothing). The HTTP response shape and the generic 401 message are untouched — this only adds an internal side effect. Alternative considered: write from `AuthController` after the fact — rejected because the controller would have to re-derive "does this email exist" itself (a second lookup, or `LoginAsync`'s return type ballooning to leak the distinction back out where it could accidentally reach the response).

**D3 — `AccessDenied` logging is a single terminal middleware, not a policy handler or a controller filter.**
A new `Api/Middleware/AccessDeniedLoggingMiddleware` is registered **before** `UseAuthentication()`/`UseAuthorization()` in `Program.cs` and does: `await _next(context)`, then `if (context.Response.StatusCode == 403)` write an `AccessLog` row (`EventType = AccessDenied`, `UserId` from `ICurrentUserService` — null if the request never authenticated, `IpAddress` from `HttpContext.Connection.RemoteIpAddress`). Placement matters and is easy to get backwards (caught during implementation): ASP.NET Core's authorization middleware does **not** call its own `next()` when a policy fails — it short-circuits the pipeline directly. A middleware registered *after* `UseAuthorization()` would therefore never even run for a policy-denied request, since the delegate chain never reaches it. Registering it *first* means its own `next()` call wraps the entire rest of the pipeline (authentication, authorization, routing, controller execution); only then does the code after that `await` see the final, already-decided status code — whether the request was denied by the policy handler (framework-issued 403, no controller code ever ran) or by a manual `StatusCode(403)` deep inside a controller (`ForbiddenOperationException` → `GuardedAsync`, reached only because authorization already passed). This is the only placement that observes both paths with the same code, and it automatically covers every future capability's endpoints without each one adding its own logging call — matching the proposal's explicit ask to avoid case-by-case controller instrumentation. The middleware's `InvokeAsync` takes the scoped `IAccessLogRepository`/`ICurrentUserService` as method parameters (not constructor-injected, since the middleware instance itself is a singleton but these dependencies are request-scoped) — the standard ASP.NET Core pattern for scoped middleware dependencies. The write is wrapped in try/catch that logs via `ILogger` and never rethrows: a failure to persist the audit trail must not become a new failure mode for the underlying request. Alternative considered: `IAuthorizationMiddlewareResultHandler` — rejected because it only intercepts the policy-based path and would silently miss every manual `StatusCode(403)` (see Context); a `403` produced this way would go unlogged, exactly the "easy to have incomplete coverage" risk called out in the proposal's testing scope.

**D4 — `AuditLog`/`AccessLog` reads follow the `ledger-entries` list-endpoint pattern (Application service + EF repository), not `IReportQueryService`.**
New `AuditLogController`/`AccessLogController` (thin, `[Authorize]` + `GuardedAsync`-style 403 mapping) call new `AuditLogQueryService`/`AccessLogQueryService` in Application, which enforce `EnsureReader()` (Manager or Auditor; `ForbiddenOperationException` for Editor — same style as `LedgerEntryService.EnsureWriter()`) and build a `PagedRequest`/`PagedResult<T>` (reusing `Application/Common/Pagination.cs` verbatim) response via a repository method on `IAuditLogRepository`/`IAccessLogRepository` implemented with EF Core LINQ, not Dapper — this endpoint is a scoped list view over live operational data, the same category as `GET /api/ledger-entries`, not an aggregate report.

**D5 — Subsidiary scoping resolves through a join only when the caller is subsidiary-bound; a global caller reads the table directly.**
Neither `AuditLog` nor `AccessLog` carries a `SubsidiaryId` column (deliberately — see proposal "Out of Scope"). For a **global** Manager/Auditor (`ICurrentUserService.SubsidiaryId == null`), the query has nothing to resolve: read the table directly with the requested filters, no join, no risk of an unrecognized `EntityType`/event silently disappearing. For a **subsidiary-scoped** caller:
- `audit-log`: filter by joining each known `EntityType` to its owning aggregate's `SubsidiaryId` — `LedgerEntry.SubsidiaryId` for `EntityType = "LedgerEntry"`, `BankStatementImportBatch.SubsidiaryId` for `EntityType = "BankStatementImportBatch"` — unioned (`Concat` in EF Core LINQ, translates to `UNION ALL`) into one filtered, paginated query.
- `access-log`: filter by joining `User.SubsidiaryId` on `AccessLog.UserId`; rows with `UserId = null` (failed login against an unknown email) can't be attributed to any subsidiary and are excluded from a subsidiary-scoped view, visible only to a global Manager/Auditor (stated explicitly in the proposal's scenario list).
This keeps global-scope reads simple and correct by construction, and confines the join complexity to subsidiary-scoped reads only. Alternative considered: denormalize a `SubsidiaryId` column onto both tables at write time — rejected for this change (see proposal "Out of Scope"); revisit if the join-based approach becomes a real query-performance problem.

**D6 — Frontend: new `components/ui/tabs.tsx` primitive, feature folder mirrors `ledger-entries`.**
No `Tabs` primitive exists yet in this codebase. Add one as a shared `components/ui/tabs.tsx` (not hand-rolled inside the feature) so any future two/multi-tab screen reuses it. Implemented during the build as a small dependency-free primitive (React context + plain buttons/ARIA roles) rather than wrapping `@radix-ui/react-tabs` — that package isn't installed yet, and this codebase's existing `components/ui` primitives are already minimal (plain `<select>` filters throughout `ledger-entries`, no Select/Dialog primitive either); adding a new external dependency for a two-tab toggle wasn't justified. `features/audit-trail/` follows the established shape (`types.ts`, `api/`, `hooks/`, `components/AuditTrailPage.tsx` housing both tabs, each with its own filter bar + paginated table, `i18n/en.json` + `i18n/pt-BR.json`). Nav gating in `SideMenu.tsx` needs a new `isManagerOrAuditor(user)` helper in `features/auth/roles.ts` (no `isAuditor` helper exists today) and a `RequireManagerOrAuditor` route guard mirroring `features/users/components/RequireManager.tsx`.

## Risks / Trade-offs

- **[Risk] A future capability adds a new `AuditLog` `EntityType` without a matching join branch in `AuditLogQueryService`.** A subsidiary-scoped Manager/Auditor would then simply never see those rows (excluded, not leaked) while a global Manager/Auditor sees them fine. → Mitigation: the query service's join list is a single, obvious switch in one file; call this out in `tasks.md` as a note for whoever builds the next `AuditLog`-writing capability, and add an integration test asserting a subsidiary-scoped read only ever returns known, resolvable `EntityType`s (never silently includes an unresolvable one).
- **[Risk] The terminal middleware runs on every request, including ones that never touch business logic (e.g. a 403 from an unrelated framework concern, if one is ever introduced).** → Mitigation: the middleware only acts on `StatusCode == 403` and is scoped to write, never to alter the response; a no-op for the overwhelming majority of requests (any non-403 status) is cheap (one integer comparison).
- **[Risk] IP capture via `HttpContext.Connection.RemoteIpAddress` records the Docker network's internal address, not a real client IP, once this sits behind any reverse proxy/load balancer in a real deployment.** → Mitigation: accepted for MVP (local Docker Compose has no such proxy in front of the API today); flagged as an Open Question below, same family of concern as the already-roadmapped Redis rate limiting (`docs/requirements-document.md` §11).
- **[Trade-off] Writing `AccessLog` inside `AuthService` (Application layer) instead of `AuthController` (Api layer) couples the login use case to persistence of a cross-cutting concern.** Accepted because it's the only layer that already has the nullable-`UserId` distinction without re-deriving it, and it mirrors the existing `AuditLog`-from-Application-service pattern used by `LedgerEntryService`/`BankStatementImportService`.
- **[Trade-off] The `Concat`-based union query for subsidiary-scoped `audit-log` reads is less efficient than a single indexed query would be if `SubsidiaryId` were denormalized onto `AuditLog`.** Accepted for MVP data volumes (portfolio project, no real production load); revisit only if this capability's read performance is ever actually observed to be a problem.

## Migration Plan

1. EF Core migration adding `AccessLogs` table (`AccessLog` entity + `AccessLogEventType` enum-as-string, same convention as `AuditLogs.Action`).
2. No migration needed for `AuditLog`/`LedgerEntry`/`BankStatementImportBatch` — all existing columns already support the join-based scoping in D5.
3. Backend changes are purely additive (new entity, new repository, new query services, new controllers, new middleware) plus one modified method signature (`AuthService.LoginAsync` gains an `ipAddress` parameter) — no breaking change to any existing endpoint contract.
4. Frontend: new feature folder + nav link; no existing screen is modified beyond `SideMenu.tsx`'s link list.
5. Rollback: revert the migration (drops `AccessLogs`, no data loss elsewhere since no other table is altered) and revert the code changes; `AuditLog` writes/behavior are entirely unaffected since this change only adds a reader on top of them.

## Open Questions

- Should `AccessDeniedLoggingMiddleware` also capture the attempted route/method (e.g. `PathAndQuery`) for easier triage, even though `docs/requirements-document.md` §3.9 doesn't list it as a field? Leaning no for this change — stick to the documented shape; can be revisited as a follow-up if the Access Activity tab proves hard to act on without it.
- When (not if) a reverse proxy sits in front of the API in the Hostinger VPS deployment (`docs/development-workflow.md` §5), `UseForwardedHeaders` will need to be added for `IpAddress` to reflect the real client — tracked as a future concern, not blocking this change.
